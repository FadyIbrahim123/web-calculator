# Data Model: Calculation History

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Round 1's `data-model.md` described a single, ephemeral `CalculationState` that is overwritten by every action and holds nothing across calculations. This feature is different: it introduces a genuine, if session-scoped, **collection** that accumulates across multiple calculations, has its own bounded lifecycle (add, evict, clear), and is derived from — but stored outside — the engine's state. That's why this document is a full model rather than a near-empty shell.

Both entities below are held only in React component state, in memory, for the life of the current page load (spec FR-009); nothing here is written to `localStorage`, a cookie, or any backend. `CalculatorState` itself (round 1's entity) is unchanged by this feature and is not re-documented here — see [`specs/001-web-calculator/data-model.md`](../001-web-calculator/data-model.md) — but is referenced below wherever a field or transition is constrained by it.

## Entity: History Entry

Represents one calculation that completed successfully via equals. Immutable once created — nothing in this feature edits an existing entry (spec Assumptions: no rename/pin/edit of individual entries).

| Field | Type | Description | Constrained by round 1? |
|---|---|---|---|
| `id` | `string` | A locally-unique identifier for this entry, generated by the orchestration layer (`useHistory`), not the engine. Used only for React list rendering/selection — carries no calculation meaning. | No — this field exists purely because a list of entries needs stable identity; it has no round-1 counterpart. |
| `firstOperand` | `number` | The value of `CalculatorState.previousOperand` at the moment `equals` was invoked. | **Yes** — this is round 1's `previousOperand` field, captured before the engine's `equals()` clears it to `null` on success (see research.md #1). |
| `operator` | `"add" \| "subtract" \| "multiply" \| "divide"` | The operator that was applied. | **Yes** — this is exactly round 1's `Operator` type; no new operator values are introduced or renamed. |
| `secondOperand` | `number` | `Number(CalculatorState.display)` at the moment `equals` was invoked (i.e., before the display was overwritten with the result). | **Yes** — sourced from round 1's `display` field, read (never written) by this feature. |
| `result` | `string` | The formatted result string — `CalculatorState.display` *after* `equals` succeeds. Always a plain formatted number; never `"N/A"` or `"exceeded the max digits"` (see Validation rules). | **Yes** — this is round 1's own `formatResult`/digit-cap output, taken as-is. History never reformats a value the engine already formatted. |

### Validation rules (from spec Functional Requirements)

- A `History Entry` is only ever created when `equals` produces a non-error result (`isError === false` post-`equals`, per round 1's engine) — spec FR-002. Divide-by-zero (`N/A`) and any state where `equals` was a no-op (no pending operator, or repeated equals with no new input — round 1's own no-op rules) never produce an entry.
- `result` therefore can never be the literal strings `"N/A"` or `"exceeded the max digits"` — those are round-1 error states, and error states are excluded by the rule above. (If a computed result would itself overflow past round 1's 10-digit cap, round 1's `equals()` already sets `isError: true` in that case, so it too is excluded — no separate overflow handling is needed inside history.)
- `firstOperand` and `secondOperand` are plain JavaScript numbers already validated/normalized by round 1's engine (single decimal point, no leading zeros, ≤10 digits) before history ever sees them — this feature performs no additional numeric validation of its own.

## Entity: History List

The bounded, ordered collection of History Entries currently retained.

| Field | Type | Description |
|---|---|---|
| `entries` | `HistoryEntry[]` | Ordered most-recent-first (index `0` is the newest). |
| *(cap)* | `const MAX_HISTORY_ENTRIES = 5` | Not a stored field — a module-level constant enforced by `recordEntry` (spec FR-004, Clarifications: 5 entries). |

### State transitions

| Action | Effect |
|---|---|
| Record (a calculation completes successfully) | `entries = [newEntry, ...entries].slice(0, 5)`. If `entries` already had 5 items, the 6th-oldest (previously at index 4) is dropped entirely — not archived, not recoverable (Clarifications: "not shown or accessible anywhere"). |
| Reuse (`restoreState(entry)`) | Does **not** mutate the History List — spec FR-005 / User Story 2 Acceptance Scenario 4 explicitly require the list to be unchanged by selection. Instead, it returns a new `CalculatorState` (`{ display: entry.result, previousOperand: null, operator: null, awaitingSecondOperand: false, isError: false }`) for the calculator's own state to adopt, replacing whatever calculation was in progress. |
| Clear | `entries = []`. Idempotent — clearing an already-empty list is a no-op with no error (User Story 3, Acceptance Scenario 3). |

### Initial state

```text
{ entries: [] }
```

This is the state on first page load and immediately after Clear — surfaced by the UI as the empty state (spec FR-007), never as an error.

## Relationship between the two entities (and round 1)

```text
CalculatorState (round 1, engine-owned, ephemeral)
        │  observed at the moment equals() is called
        ▼
   { firstOperand, operator, secondOperand, result }  ──record──▶  History Entry  ──┐
        ▲                                                                            │ stored in
        │  restoreState()                                                           ▼
        └───────────────────────────────────────────────────────────────  History List (this feature)
```

History Entries are a **read-only projection** of moments in the engine's lifecycle — the engine never queries, imports from, or holds a reference to `history.ts` or the History List. Data flows in one direction outward (engine → history) for recording, and a restored value flows back in only as an ordinary, already-valid `CalculatorState` (reuse) — the same shape the engine already knows how to accept and continue from, not a new kind of input the engine has to learn to understand. This one-directional, read-only relationship is what keeps FR-010/FR-011 (round 1's behavior and the engine's purity both preserved) true by construction rather than by convention.
